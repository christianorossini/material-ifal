7.1

Introdução

Nos capítulos 5 e 6 vimos que um sistema multiprogramável executa vários processos e threads concorrentemente. Muitas vezes eles não são independentes: cooperam para realizar uma tarefa e, para isso, compartilham recursos como memória, arquivos e dispositivos.

Um exemplo simples: um processo grava dados num buffer e outro processo lê esses dados. Para dar certo, o leitor não pode ler um buffer vazio, o gravador não pode gravar num buffer cheio, e os dois não podem mexer na mesma posição ao mesmo tempo.

Ideia central

Os mecanismos de sincronização garantem que a comunicação e o compartilhamento de recursos entre processos concorrentes aconteçam de forma ordenada e correta.

O capítulo responde a duas perguntas. A primeira é quem usa o recurso agora? Quando dois processos disputam o mesmo dado, é preciso garantir que um espere o outro terminar: é a exclusão mútua (seções 7.4 a 7.7). A segunda é quando posso continuar? Quando um processo depende de algo que outro ainda vai produzir, é preciso que ele espere o momento certo: é a sincronização condicional (seção 7.8). Semáforos, monitores e troca de mensagens (7.9 a 7.11) são ferramentas para resolver as duas. O capítulo termina com o deadlock (7.12), o problema que surge quando a espera nunca acaba.

Tudo isso vale tanto para processos quanto para threads. Como os threads de um processo compartilham a memória, os problemas de sincronização aparecem com eles com ainda mais frequência.

7.2

Aplicações concorrentes

Uma aplicação concorrente é formada por vários processos ou threads que executam ao mesmo tempo e cooperam para resolver um problema. Exemplos: um servidor que atende vários clientes, um editor que grava em segundo plano enquanto o usuário digita, um sistema bancário com vários caixas.

Os processos de uma aplicação concorrente se comunicam de duas formas:

Variáveis compartilhadas

Os processos leem e escrevem numa mesma área de memória. É rápido, mas exige controle para que dois processos não alterem o mesmo dado ao mesmo tempo.

Troca de mensagens

Um processo envia uma mensagem e o outro a recebe, com o SO como intermediário. Funciona até entre processos em computadores diferentes (seção 7.11).

Nos dois casos, os processos precisam sincronizar suas ações: um só deve ler o dado depois que o outro o tiver gravado.

Na memória compartilhada, o SO só entra para criar a área comum; depois, os processos a acessam diretamente, como acessam qualquer variável, e a responsabilidade de coordenar o acesso é do programa. Na troca de mensagens, cada envio e cada recebimento passa pelo SO, o que é mais lento, mas a sincronização vem embutida: quem espera uma mensagem só continua quando ela chega.

No Windows

Canais de comunicação que já existem na sua máquina

Programas do Windows conversam o tempo todo por pipes nomeados, um mecanismo de troca de mensagens. O PowerShell lista os que estão abertos agora:

# cada nome é um canal que algum processo criou para receber mensagens
PS> Get-ChildItem \\.\pipe\ | Select-Object -First 15 Name

Para memória compartilhada, o Windows oferece os arquivos mapeados em memória: dois processos mapeiam a mesma área e passam a enxergar os mesmos bytes. Os laboratórios de SO usam pipes e uma "caixa postal" em pasta para mostrar a troca de mensagens na prática.

7.3

Especificação de concorrência em programas

Para escrever uma aplicação concorrente, a linguagem precisa permitir indicar quais partes do programa podem executar ao mesmo tempo. Duas notações clássicas:

  • FORK e JOIN: FORK cria um novo processo que executa em paralelo com o que o criou; JOIN faz o processo esperar até que o outro termine.
  • PARBEGIN e PAREND (ou COBEGIN e COEND): os comandos entre as duas palavras executam concorrentemente, e o programa só continua depois que todos terminam.
PROGRAM Expressao;
VAR X, Temp1, Temp2, Temp3 : REAL;
BEGIN
  PARBEGIN
    Temp1 := SQRT (1024);     { os três cálculos executam }
    Temp2 := 35.4 * 0.23;     { ao mesmo tempo           }
    Temp3 := 302 / 7;
  PAREND;                      { espera os três terminarem }
  X := Temp1 + Temp2 - Temp3;
  WRITELN ('x = ', X);
END.

Repare no que permite a concorrência: Temp1, Temp2 e Temp3 não dependem uns dos outros, então a ordem em que são calculados não altera o resultado. Já X só pode ser calculado depois dos três. Identificar essas dependências é o primeiro passo para escrever qualquer aplicação concorrente. Com FORK e JOIN, o mesmo programa ficaria assim:

FORK Calcula_Temp1;     { cria um processo para cada cálculo }
FORK Calcula_Temp2;
Temp3 := 302 / 7;       { o processo original faz o terceiro }
JOIN Calcula_Temp1;     { espera os outros dois terminarem }
JOIN Calcula_Temp2;
X := Temp1 + Temp2 - Temp3;
Hoje

A mesma ideia aparece ao criar threads e esperar por elas, como pthread_create e pthread_join, vistos no capítulo 6.

No Windows

FORK e JOIN no PowerShell

Cada Start-Job cria um processo que executa em segundo plano (o FORK); Receive-Job -Wait espera o resultado (o JOIN).

PS> $j1 = Start-Job { [math]::Sqrt(1024) }      # FORK
PS> $j2 = Start-Job { 35.4 * 0.23 }             # FORK
PS> $t3 = 302 / 7                               # o próprio PowerShell calcula
PS> $t1 = Receive-Job $j1 -Wait                 # JOIN
PS> $t2 = Receive-Job $j2 -Wait                 # JOIN
PS> $t1 + $t2 - $t3
7.4

Problemas de compartilhamento de recursos

O livro mostra o problema com uma conta bancária. Dois caixas executam o mesmo programa ao mesmo tempo: cada um lê o saldo do cliente, calcula o novo valor e grava. Se o caixa 1 (saque de 200) e o caixa 2 (depósito de 300) leem o saldo de 1000 antes que qualquer um grave, o último a gravar apaga a operação do outro: o saldo final fica 800 ou 1300, quando deveria ser 1100.

O mesmo acontece com um comando tão simples quanto X := X + 1. Em linguagem de máquina, ele vira três instruções: carregar X num registrador, somar 1 e gravar de volta. Se o processo perde a UCP no meio delas, outro processo pode ler o valor antigo de X.

OrdemProcesso A (X := X + 1)Processo B (X := X − 1)X na memória
1LOAD X, Ra → Ra = 22
2ADD 1, Ra → Ra = 32
3perde a UCPLOAD X, Rb → Rb = 22
4SUB 1, Rb → Rb = 12
5STORE Ra, X3
6STORE Rb, X1

A tabela mostra uma das ordens possíveis. X começou em 2 e deveria terminar em 2, mas termina em 1: a alteração de A se perdeu, porque B leu X antes de A gravar. O problema não está em nenhum dos dois programas isoladamente, e sim na intercalação das instruções, que depende de quando o SO troca de processo.

Condição de corrida

Quando o resultado depende da ordem em que os processos executam, dizemos que há uma condição de corrida (race condition). O erro aparece só às vezes, o que o torna difícil de encontrar.

Condições de corrida são traiçoeiras porque o programa funciona na maior parte das vezes. A troca de processo precisa acontecer exatamente entre a leitura e a gravação para o erro aparecer. Em testes rápidos, isso quase nunca acontece; com milhares de usuários, acontece todo dia.

No Windows

Dois caixas, um arquivo

Abra duas janelas do PowerShell. O arquivo saldo.txt faz o papel da conta. O Start-Sleep alarga o intervalo entre ler e gravar, para que a corrida aconteça com certeza.

# nas DUAS janelas
PS> $arq = "$env:USERPROFILE\Desktop\saldo.txt"
# janela 1: cria a conta com 1000 e faz um saque de 200
PS> Set-Content $arq 1000
PS> $s = [int](Get-Content $arq); Start-Sleep 15; Set-Content $arq ($s - 200)
# janela 2, logo em seguida (antes de 15 s): depósito de 300
PS> $s = [int](Get-Content $arq); Start-Sleep 15; Set-Content $arq ($s + 300)
# depois que as duas terminarem
PS> Get-Content $arq            # 1300, e não 1100

O saque se perdeu, como no exemplo do livro. O Laboratório 1 de SO faz esta experiência passo a passo e mostra como corrigi-la trancando o arquivo.

7.5

Exclusão mútua

A forma de evitar esses problemas é impedir que dois processos acessem o recurso compartilhado ao mesmo tempo. Enquanto um processo usa o recurso, os outros que querem usá-lo esperam. Essa ideia se chama exclusão mútua.

A parte do código em que o processo acessa o recurso compartilhado é a região crítica. Garantir exclusão mútua é garantir que dois processos nunca estejam ao mesmo tempo nas suas regiões críticas. Para isso, cada processo executa um protocolo de entrada antes da região crítica e um protocolo de saída depois:

BEGIN
  ...
  Entra_Regiao_Critica;    { protocolo de entrada }
  Regiao_Critica;          { acesso ao recurso compartilhado }
  Sai_Regiao_Critica;      { protocolo de saída }
  ...
END.

Só a região crítica precisa ser protegida. O resto do código, que lida com dados próprios de cada processo, pode executar livremente em paralelo. Por isso, uma boa prática é manter a região crítica o menor possível: quanto mais tempo um processo fica nela, mais tempo os outros esperam.

No exemplo do banco, a região crítica é o trecho entre ler o saldo e gravar o novo valor. Se o caixa 2 só pudesse ler o saldo depois que o caixa 1 tivesse gravado, o resultado seria sempre 1100, em qualquer ordem.

Uma boa solução de exclusão mútua também precisa evitar:

  • Starvation (inanição): um processo esperar indefinidamente para entrar na região crítica, porque outros sempre passam na frente.
  • Um processo que está fora da sua região crítica impedir que os outros entrem.
  • Depender da velocidade relativa dos processos ou do número de processadores.
No Windows

"O arquivo está aberto em outro programa"

Abra um documento no Word ou uma planilha no Excel e, com ele aberto, tente renomear ou excluir o arquivo no Explorador de Arquivos. O Windows recusa: o Office abriu o arquivo pedindo acesso exclusivo, e o SO garante a exclusão mútua sobre ele. Feche o documento e tente de novo: agora funciona. O Bloco de Notas não pede esse acesso exclusivo, por isso não bloqueia o arquivo.

7.6

Soluções de hardware para a exclusão mútua

Desabilitação de interrupções

A solução mais simples: o processo desabilita as interrupções ao entrar na região crítica e as reabilita ao sair. Sem interrupções, o SO não consegue tirar a UCP do processo, então nenhum outro executa enquanto ele está na região crítica.

Problemas: se um processo de usuário esquecer de reabilitar as interrupções, o sistema inteiro para; e, com vários processadores, desabilitar as interrupções de um deles não impede que os outros continuem executando. Por isso, só o núcleo do SO usa esse recurso, e por pouco tempo.

Instrução test-and-set

Muitos processadores têm uma instrução especial que lê o valor de uma variável e a altera numa única operação indivisível (atômica). Com ela, uma variável de bloqueio indica se a região crítica está ocupada:

repete
   Test_And_Set (Bloqueio)   { lê e marca como ocupado, atomicamente }
até encontrar livre;
Regiao_Critica;
Bloqueio := falso;           { libera }

Por que precisa ser uma instrução só? Se o teste e a alteração fossem duas instruções separadas, dois processos poderiam testar a variável, ambos encontrá-la livre e ambos entrar. É a mesma condição de corrida que se quer evitar. Executada como uma única instrução, que o hardware não deixa ser interrompida no meio nem intercalada com outro processador, ela fecha essa brecha.

Problemas: enquanto espera, o processo fica testando a variável sem parar, gastando UCP (espera ocupada), e a escolha de quem entra é arbitrária, o que permite starvation.

Nos processadores atuais

Os processadores x86 têm instruções como XCHG e LOCK CMPXCHG, que fazem o papel do test-and-set. O Windows as usa nas funções InterlockedIncrement e InterlockedCompareExchange, e o núcleo as usa nos spinlocks, travas de espera ocupada usadas por trechos curtíssimos, em que bloquear e acordar o processo custaria mais do que esperar.

7.7

Soluções de software para a exclusão mútua

O livro apresenta uma sequência de algoritmos que tentam garantir exclusão mútua usando apenas variáveis do programa. Os quatro primeiros falham: um obriga os processos a alternar a vez, outro deixa dois entrarem juntos, outro leva a deadlock, outro a starvation. A primeira solução correta para dois processos foi o algoritmo de Dekker. Em 1981, Peterson apresentou uma solução bem mais simples:

{ processo i; o outro processo é j }
quer[i] := verdadeiro;            { eu quero entrar }
vez := j;                         { mas dou a vez ao outro }
enquanto quer[j] e vez = j:       { espero só se ele também quer }
    espera;                       { e a vez é dele }
Regiao_Critica;
quer[i] := falso;
TentativaIdeiaPor que falha
1Uma variável vez diz quem pode entrar; ao sair, o processo passa a vez ao outro.Os processos são obrigados a alternar. Se um quer entrar duas vezes seguidas e o outro não quer entrar, o primeiro fica esperando por alguém que está fora da região crítica.
2Cada processo tem uma variável que indica se está dentro; antes de entrar, testa a do outro.Os dois podem testar ao mesmo tempo, ver o outro fora e entrar juntos. Não garante exclusão mútua.
3Cada processo primeiro declara que quer entrar e só depois testa o outro.Se os dois declaram ao mesmo tempo, cada um espera o outro desistir. Deadlock.
4Como a 3, mas quem encontra o outro querendo entrar desiste por um instante e tenta de novo.Os dois podem desistir e tentar sempre ao mesmo tempo, indefinidamente. Starvation.

O algoritmo de Peterson junta a ideia da tentativa 3 (declarar que quer entrar) com a variável vez da tentativa 1, usada só como desempate. Se só um processo quer entrar, ele entra direto. Se os dois querem, quem escreveu vez por último cede a vez, e o outro entra.

7.8

Sincronização condicional

Às vezes não basta impedir o acesso simultâneo: um processo precisa esperar até que uma condição seja verdadeira para continuar. Isso é a sincronização condicional.

O exemplo clássico é o produtor/consumidor com buffer limitado: o produtor grava dados num buffer de N posições e o consumidor os lê. O produtor precisa esperar quando o buffer está cheio, e o consumidor precisa esperar quando ele está vazio. Além disso, o acesso ao buffer em si exige exclusão mútua.

O buffer costuma ser implementado como um vetor circular: o produtor grava na posição indicada por um índice de entrada e o avança; o consumidor lê na posição indicada por um índice de saída e também o avança. Ao chegar ao fim do vetor, os índices voltam ao início. Um contador indica quantas posições estão ocupadas.

Note que há duas exigências diferentes no mesmo problema. A exclusão mútua impede que produtor e consumidor alterem o contador e os índices ao mesmo tempo. A sincronização condicional faz cada um esperar enquanto a sua condição não for verdadeira. Uma solução correta precisa das duas.

Resolver isso com espera ocupada desperdiça UCP. As próximas seções mostram como fazer o processo realmente dormir até a condição mudar.

7.9

Semáforos

Proposto por E. W. Dijkstra em 1965, o semáforo é uma variável inteira, não negativa, que só pode ser manipulada por duas operações, executadas de forma indivisível:

DOWN (S) · também chamada P

Se S > 0, decrementa S e o processo continua. Se S = 0, o processo vai para o estado de espera, numa fila associada ao semáforo.

UP (S) · também chamada V

Se há processos esperando no semáforo, acorda um deles. Se não há, incrementa S.

Por dentro, o semáforo é uma estrutura do SO com dois campos: o valor e uma fila de processos bloqueados. DOWN e UP são chamadas de sistema. Para que sejam indivisíveis, o SO as executa protegidas por um dos mecanismos de hardware da seção 7.6, mas apenas pelas poucas instruções que alteram o valor e a fila. A espera longa, a do processo que não pode entrar, acontece com o processo bloqueado, fora da UCP.

Como o processo bloqueado fica em espera, e não testando uma variável, não há espera ocupada. Semáforos que só assumem 0 e 1 são binários (mutexes) e servem para exclusão mútua; os que vão de 0 a N são contadores e servem para controlar recursos com várias unidades e para sincronização condicional.

No Windows

Um semáforo de verdade, em três janelas

O Windows oferece semáforos e mutexes como objetos do sistema, que vários processos podem usar pelo nome. Abra três janelas do PowerShell e, em cada uma, execute:

PS> $s = New-Object System.Threading.Semaphore(2, 2, 'AulaSO')   # valor inicial 2
PS> $s.WaitOne()          # DOWN: True quando consegue entrar

As duas primeiras janelas entram na hora; a terceira fica parada, bloqueada pelo SO, sem gastar UCP. Na primeira janela, execute $s.Release() (o UP): a terceira janela acorda e entra. É o semáforo contador do simulador acima, agora entre processos reais. No Laboratório 2 de SO a experiência é guiada passo a passo.

Sincronização condicional com semáforos

O produtor/consumidor usa três semáforos: Vazio conta as posições livres (começa em N), Cheio conta as ocupadas (começa em 0) e Mutex protege o acesso ao buffer.

Produtor:                    Consumidor:
REPEAT                       REPEAT
  Produz_Dado;                 DOWN (Cheio);   { espera ter dado }
  DOWN (Vazio);  { espera vaga }  DOWN (Mutex);
  DOWN (Mutex);                Le_Buffer;
  Grava_Buffer;                UP (Mutex);
  UP (Mutex);                  UP (Vazio);     { avisa: uma vaga a mais }
  UP (Cheio);    { avisa }      Consome_Dado;
UNTIL False;                 UNTIL False;

Problemas clássicos

A ordem dos DOWN importa. Se o produtor fizesse DOWN (Mutex) antes de DOWN (Vazio) com o buffer cheio, ele bloquearia segurando o Mutex; o consumidor, para liberar uma posição, precisaria do Mutex, e nunca o conseguiria. Os dois ficariam parados para sempre: um deadlock causado só pela troca de duas linhas. É esse tipo de erro que torna os semáforos difíceis de usar e que motiva os monitores (7.10).

Leitores e escritores. Vários processos leem um dado e alguns o alteram. Vários leitores podem ler ao mesmo tempo, mas um escritor precisa de acesso exclusivo: enquanto ele escreve, ninguém lê nem escreve. A solução clássica usa um contador de leitores ativos: o primeiro leitor a chegar bloqueia os escritores, e o último a sair os libera. Ela tem um efeito colateral: se sempre houver algum leitor lendo, o escritor pode esperar para sempre (starvation). Há variantes que dão prioridade aos escritores.

Jantar dos filósofos. Cinco filósofos sentam a uma mesa redonda, com um garfo entre cada dois. Para comer, cada um precisa dos dois garfos ao seu lado. Se todos pegarem o garfo da esquerda ao mesmo tempo, ninguém consegue o da direita: deadlock. Soluções: permitir no máximo quatro filósofos à mesa; pegar os dois garfos só se ambos estiverem livres (de forma atômica); ou fazer os filósofos ímpares pegarem primeiro o garfo da esquerda e os pares, o da direita.

7.10

Monitores

Semáforos resolvem o problema, mas são fáceis de usar errado: um DOWN esquecido, ou dois DOWN na ordem trocada, causam inconsistência ou deadlock. Os monitores, propostos por Brinch Hansen e Hoare no início dos anos 1970, são um mecanismo de alto nível que tira essa responsabilidade do programador.

Um monitor agrupa variáveis, procedimentos e um código de inicialização. As variáveis só podem ser acessadas pelos procedimentos do próprio monitor, e o compilador garante que apenas um processo por vez execute um procedimento do monitor. Os demais esperam numa fila de entrada. A exclusão mútua é automática.

A diferença para os semáforos está em quem cuida da exclusão mútua. Com semáforos, cada programador precisa lembrar de chamar DOWN e UP nos lugares certos, em todos os pontos do código que acessam o dado. Com monitores, o acesso ao dado só é possível pelos procedimentos do monitor, e o compilador gera sozinho o controle de entrada e saída. Um erro de esquecimento deixa de ser possível.

Para a sincronização condicional, o monitor usa variáveis de condição com duas operações:

  • WAIT (C): o processo espera na fila da condição C e libera o monitor para outro processo;
  • SIGNAL (C): acorda um processo que espera na condição C.
MONITOR Buffer;
  VAR Cheio, Vazio : CONDITION;
  PROCEDURE Produz;
    IF Cont = TamBuf THEN WAIT (Cheio);
    grava no buffer; Cont := Cont + 1;
    IF Cont = 1 THEN SIGNAL (Vazio);
  PROCEDURE Consome;
    IF Cont = 0 THEN WAIT (Vazio);
    lê do buffer; Cont := Cont - 1;
    IF Cont = TamBuf - 1 THEN SIGNAL (Cheio);
END.

Ao chamar WAIT, o processo libera o monitor; se não liberasse, ninguém conseguiria entrar para mudar a condição que ele espera. Quando outro processo chama SIGNAL, é preciso decidir quem continua dentro do monitor, o que sinalizou ou o que foi acordado, porque os dois não podem estar lá ao mesmo tempo. Hoare propôs que o acordado execute primeiro; muitas linguagens atuais fazem o contrário, e por isso nelas o processo acordado precisa testar a condição de novo, num laço, antes de prosseguir.

Hoje

Os métodos synchronized de Java, com wait() e notify(), funcionam como um monitor. Em C#, a instrução lock e a classe Monitor (com Monitor.Wait e Monitor.Pulse) fazem o mesmo papel; em Python, threading.Condition.

7.11

Troca de mensagens

A troca de mensagens permite comunicação e sincronização sem memória compartilhada, usando duas rotinas: SEND (Receptor, Mensagem) e RECEIVE (Transmissor, Mensagem). O SO cuida do canal, que pode ligar até processos em computadores diferentes.

Comunicação direta

Cada processo nomeia explicitamente o outro. Simples, mas, se o nome de um processo mudar, o código do outro também muda.

Comunicação indireta

As mensagens vão para uma área intermediária, a mailbox (caixa postal) ou porta, que pode ser usada por vários processos.

Quanto à sincronização, a troca pode ser:

  • Síncrona (rendezvous): quem envia fica esperando até a mensagem ser recebida, e quem recebe espera até a mensagem chegar. Não precisa de buffer, mas limita a concorrência.
  • Assíncrona: quem envia não espera; a mensagem fica num buffer até ser lida. Aumenta a eficiência das aplicações, mas exige buffers e mecanismos para saber se a mensagem foi recebida.

Também é preciso tratar a perda de mensagens: o receptor envia uma confirmação (ACK), e o transmissor reenvia a mensagem se a confirmação não chegar. Se a confirmação é que se perdeu, o receptor recebe a mesma mensagem duas vezes; por isso as mensagens costumam levar um número de sequência, que permite descartar as repetidas. Entre computadores diferentes, ainda é preciso identificar os processos na rede e, muitas vezes, garantir que ninguém leia ou altere as mensagens no caminho.

As variações podem ser combinadas. Uma forma comum é a assíncrona no envio e bloqueante no recebimento: quem envia continua trabalhando, e quem chama RECEIVE espera até haver mensagem. É assim que funcionam, por exemplo, as filas de mensagens usadas entre serviços de um sistema web.

No Windows

As janelas conversam por mensagens

Todo programa com janela no Windows é guiado por uma fila de mensagens: cada clique, tecla ou pedido de redesenho chega como uma mensagem que o programa retira da fila e trata. O próprio Windows oferece as duas formas de envio do livro. SendMessage é síncrona: quem envia só continua depois que a janela de destino tratou a mensagem. PostMessage é assíncrona: a mensagem é colocada na fila e quem enviou segue em frente.

Quando um programa fica muito tempo sem retirar mensagens da fila, o Windows marca a janela como Não respondendo: as mensagens estão se acumulando sem ninguém para recebê-las.

7.12

Deadlock

Deadlock é a situação em que um processo espera por um recurso que nunca estará disponível ou por um evento que nunca vai ocorrer. O caso típico: o processo P1 tem o recurso R1 e quer R2; o processo P2 tem R2 e quer R1. Nenhum libera o que tem enquanto espera, e os dois ficam parados para sempre.

Deadlock não é o mesmo que starvation. No starvation, o processo poderia ser atendido, mas outros sempre passam na frente; basta mudar a política para que ele avance. No deadlock, um grupo de processos espera uns pelos outros num círculo, e nenhuma política de escolha resolve: sem uma intervenção, ninguém sai do lugar.

Para haver deadlock, quatro condições precisam ocorrer ao mesmo tempo:

  1. Exclusão mútua: cada recurso só pode estar alocado a um processo por vez.
  2. Espera por recurso: um processo retém recursos enquanto espera por outros.
  3. Não preempção: um recurso não pode ser retirado de um processo só porque outro o deseja.
  4. Espera circular: existe uma cadeia em que cada processo espera um recurso que está com o próximo.
Simulador

Nenhum recurso alocado.

O grafo de alocação de recursos usado no simulador é a forma clássica de enxergar o problema: processos e recursos são nós; uma seta do recurso para o processo indica que o recurso está alocado a ele; uma seta do processo para o recurso indica que o processo espera por ele. Quando cada recurso tem uma única unidade, haver um ciclo no grafo significa haver deadlock.

7.12.1 Prevenção

As estratégias contra o deadlock se dividem em três grupos: não deixar que ele aconteça (prevenção, e a variante de evitá-lo a cada pedido), deixar que aconteça e descobri-lo (detecção) e desfazê-lo depois de descoberto (correção).

Garantir que uma das quatro condições nunca ocorra. Exemplos: exigir que o processo peça todos os recursos de uma vez (sem espera por recurso); permitir retirar recursos de um processo (preempção); numerar os recursos e obrigar a pedi-los sempre em ordem crescente (sem espera circular). Cada forma tem custo, como desperdício de recursos ou starvation. Outra abordagem é o algoritmo do banqueiro, de Dijkstra: o SO só concede um recurso se o sistema continuar num estado seguro, o que exige saber de antemão o máximo que cada processo vai pedir.

Condição negadaComoCusto
Exclusão mútuaTornar o recurso compartilhável, por exemplo com spooling (só o spooler acessa a impressora).Nem todo recurso pode ser compartilhado.

O algoritmo do banqueiro recebe esse nome por imitar um banco que só empresta se, mesmo emprestando, ainda tiver como atender todos os clientes até o fim. Um estado é seguro se existe alguma ordem em que todos os processos conseguem obter o máximo que declararam, terminar e devolver tudo. Antes de atender um pedido, o SO simula o atendimento e verifica se o estado continua seguro; se não continuar, o processo espera, mesmo havendo recursos livres.

Simulador

O algoritmo do banqueiro

O sistema tem 12 unidades de um recurso (por exemplo, unidades de fita). Cada processo declarou quanto pode pedir no máximo. Faça pedidos de 1 unidade e veja quando o SO atende e quando manda esperar.

7.12.2 Detecção

Deixar o deadlock acontecer e procurá-lo: o SO mantém estruturas com os recursos alocados e os pedidos pendentes de cada processo e, periodicamente, procura espera circular. Quanto mais frequente a verificação, mais UCP ela consome.

Há um compromisso na escolha do momento. Verificar a cada pedido de recurso descobre o deadlock assim que ele surge, mas custa caro. Verificar de tempos em tempos, ou quando a UCP fica ociosa por muito tempo, custa menos, mas o deadlock pode durar até a próxima verificação, com os processos envolvidos parados.

7.12.3 Correção

Depois de detectado, o deadlock é desfeito eliminando um ou mais processos do ciclo, liberando seus recursos (escolhidos, por exemplo, por prioridade ou tempo de execução), ou fazendo rollback: voltar um processo a um ponto anterior, liberando os recursos obtidos depois dele.

Eliminar processos é simples, mas perde o trabalho que eles já fizeram; por isso costuma-se escolher a vítima pelo menor prejuízo: o processo com menor prioridade, o que executou por menos tempo ou o que tem menos recursos. O rollback preserva parte do trabalho, mas exige que o sistema guarde pontos de retorno (checkpoints) durante a execução.

No Windows

Quem resolve o deadlock?

Como a maioria dos sistemas de uso geral, o Windows não procura deadlocks entre os programas do usuário: na prática, eles são raros, e prevenir ou detectar sempre custaria caro. Se dois programas travam um esperando o outro, o efeito visível é uma janela em Não respondendo, e a correção fica com você: Finalizar tarefa, que é exatamente a eliminação de um processo do ciclo.

Já os gerenciadores de banco de dados, como o SQL Server, fazem detecção e correção automáticas: quando duas transações se bloqueiam em ciclo, o servidor escolhe uma delas como "vítima", desfaz o que ela fez (rollback) e devolve um erro ao programa, que pode tentar de novo. O Laboratório 2 de SO provoca um deadlock real com dois mutexes do Windows.
